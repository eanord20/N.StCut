# Code Audit — N.StCut (UI/WPF слой)

Аудит проведён как Senior C# / WPF Architect. Цель — найти корневую причину "сжатия" таблицы деталей при добавлении строк и оценить архитектуру UI-слоя (`NStCut.App`). **Изменения в код не вносились** — документ только фиксирует находки.

Проанализированы: `MainWindow.xaml` / `MainWindow.xaml.cs`, `ViewModels/MainViewModel.cs`, `AppTheme.xaml`, `App.xaml`, `Views/MaterialsWindow.xaml(.cs)`, `ViewModels/MaterialsViewModel.cs`, `Models/PartRow.cs`, `Models/MaterialRow.cs`, `Commands/RelayCommand.cs`, `Converters/*`.

---

# Общая оценка архитектуры (0–10): 6/10

MVVM выдержан достаточно строго (View почти не содержит логики, кроме drag&drop и обработки кликов, которые не выразить чисто через биндинги), команды и `INotifyPropertyChanged` реализованы вручную, но последовательно. Основная проблема — не архитектурный слой сам по себе, а **несогласованность между стилевой системой MaterialDesign и кастомизацией `DataGrid`/`GroupStyle`**: команда уже один раз наступила на эти грабли (см. комментарий в `AppTheme.xaml` про `Button`) и исправила для кнопок, но не для `Expander`, использованного в заголовках групп таблицы — это и есть корень репортуемого бага. Также есть чрезмерно частые вызовы `CollectionView.Refresh()`, дублирование drag&drop кода между двумя окнами, и производительность, которая деградирует линейно/квадратично с ростом числа строк из-за отключённой виртуализации и `O(n)`-компаратора сортировки.

## Critical Issues

### C1. `Expander` в `SectionGroupItemStyle` не защищён от implicit-стиля MaterialDesign — та же категория бага, что уже была исправлена для `Button`

- **Файл**: <ref_file file="D:\My_project\N.StCut\src\NStCut.App\MainWindow.xaml" />
- **Строки**: 32–48 (`SectionGroupItemStyle`), непосредственно `<Expander ...>` на строке 36
- **Описание**: `GroupStyle.ContainerStyle` определяет `ControlTemplate` для `GroupItem`, внутри которого создаётся `<Expander IsExpanded="True" ...>` **без атрибута `Style`**. `App.xaml` подключает `MaterialDesignTheme.Light.xaml` + `MaterialDesignTheme.Defaults.xaml`, которые регистрируют **implicit-стили** (без `x:Key`, по `TargetType`) для стандартных WPF-контролов, включая `Expander` — то есть этот "голый" `Expander` автоматически получает полноценный MaterialDesign-вид: свой контрол-темплейт с ToggleButton-заголовком, отступами/`MinHeight`, а также анимацию раскрытия/закрытия содержимого (переход по высоте).
- **Почему возникает**: сам проект уже документирует эту категорию проблемы — см. комментарий в <ref_file file="D:\My_project\N.StCut\src\NStCut.App\AppTheme.xaml" /> (строки 14–20): *"Implicit-стиль применялся бы ко ВСЕМ кнопкам в приложении... там принудительные Padding/MinHeight/Margin ломали раскладку строки настолько, что вся строка/заголовки таблицы переставали корректно отрисовываться"*. Именно поэтому для `Button` завели именованный `AppButtonStyle` и применяют его точечно. Для `Expander`, используемого в `GroupStyle` (то есть внутри `DataGrid`, в критичном для раскладки месте — заголовок каждой группы/раздела материала), аналогичного исключения не сделали.
- **Рекомендация**: явно указать `Style="{x:Null}"` (или собственный минимальный стиль без анимаций/лишних отступов) на `Expander` в `SectionGroupItemStyle`, по аналогии с тем, как уже сделано для кнопок.

### C2. `RowsView.Refresh()` вызывается на каждое единичное изменение строки — избыточный полный Reset вместо инкрементального обновления

- **Файл**: <ref_file file="D:\My_project\N.StCut\src\NStCut.App\ViewModels\MainViewModel.cs" />
- **Строки**: 288 (`OnRowsCollectionChanged` → `RecomputeSectionNumbers()`), 326 (`OnRowPropertyChanged`, при смене `MaterialId`), 265 (`MoveRowToMaterial`), 354 (`RowsView.Refresh()` внутри `RecomputeSectionNumbers`)
- **Описание**: `RowsView` — это `ListCollectionView` с группировкой (`PropertyGroupDescription`) и `CustomSort`. `ListCollectionView.Refresh()` эквивалентен `NotifyCollectionChangedAction.Reset` для всех подписанных `ItemsControl` — WPF в ответ **полностью уничтожает и заново создаёт все контейнеры элементов**, включая контейнеры групп (`GroupItem`, то есть каждый `Expander` из C1). Это вызывается **при каждом добавлении/удалении одной строки** (клик "Add Row", Drag&Drop строки между разделами, смена материала в ComboBox ячейки) — то есть на самое частое, "мелкое" действие пользователя навешан самый дорогой из возможных путей обновления.
- **Почему возникает**: `RecomputeSectionNumbers()` нужно вызывать, чтобы пересчитать `RowNumberInSection` и чтобы `CustomSort` (`RowSectionComparer`) корректно расставил строки по разделам — но обновление данных (`RowNumberInSection`) само по себе уже вызывает re-render соответствующих ячеек через `INotifyPropertyChanged`; жёсткий `Refresh()` для этого не обязателен в большинстве случаев (WPF grouping умеет инкрементально реагировать на `Add`/`Remove`/`Replace` из `ObservableCollection`, если явно не форсировать `Reset`).
- **Рекомендация**: не вызывать `Refresh()` при точечных изменениях; либо использовать `RowsView.DeferRefresh()` в момент батчевых операций (уже частично сделано через `_suspendRecompute`, но `Refresh()` всё равно бьёт по всей коллекции в конце), либо перейти на группировку не через `PropertyGroupDescription`+`CustomSort`, а на уже отсортированный/сгруппированный источник (например, `Rows` хранить уже в нужном порядке и не полагаться на `CollectionView.Refresh()` для перегруппировки).

### C3. `EnableRowVirtualization="False"` + `EnableColumnVirtualization="False"` усиливают эффект C1/C2 квадратичной стоимостью перестройки

- **Файл**: <ref_file file="D:\My_project\N.StCut\src\NStCut.App\MainWindow.xaml" />, строка 243
- **Описание**: при выключенной виртуализации **все** строки и колонки таблицы всегда полностью реализованы (созданы как визуальные элементы), независимо от того, видны они на экране или нет. Каждый `Refresh()` (C2) в таком режиме means "снести и заново построить визуальное дерево для абсолютно всех строк во всех группах", а не только для видимых — отсюда и заметный "скачок"/сжатие раскладки на весь список, а не только в области видимости.
- **Почему возникает**: судя по всему, виртуализация была отключена как обходной путь для другой проблемы совместимости группировки с виртуализацией (частый источник багов в `DataGrid` с `GroupStyle`), но такое решение "вслепую" резко увеличивает стоимость каждого `Refresh()` из C2 и делает C1 более заметным визуально.
- **Рекомендация**: после устранения C1 и снижения частоты `Refresh()` (C2) — попробовать вернуть `EnableRowVirtualization="True"` (виртуализацию колонок можно оставить выключенной, так как колонок немного и все фиксированной ширины) и убедиться, что группировка с виртуализацией больше не даёт визуальных артефактов.

### C4. Дублирование drag&drop-логики между `MainWindow.xaml.cs` и `MaterialsWindow.xaml.cs`

- **Файлы**: <ref_file file="D:\My_project\N.StCut\src\NStCut.App\MainWindow.xaml.cs" /> (строки 37–68), <ref_file file="D:\My_project\N.StCut\src\NStCut.App\Views\MaterialsWindow.xaml.cs" /> (строки 30–54)
- **Описание**: логика "запомнить кандидата на строке → отследить порог перемещения мыши (`SystemParameters.MinimumHorizontalDragDistance`/`Vertical...`) → инициировать `DragDrop.DoDragDrop`" продублирована почти дословно для `PartRow` и для `MaterialRow` — отличаются только тип перетаскиваемого объекта и имена полей.
- **Почему возникает**: оба окна реализовывались независимо без выделения общего инфраструктурного класса для "перетаскивания строки DataGrid".
- **Рекомендация**: вынести общий generic-хелпер (например, `DataGridRowDragHelper<T>`), инкапсулирующий проверку порога и вызов `DoDragDrop`, и переиспользовать в обоих окнах.

## Root Cause Analysis

**Почему таблица "сжимается" при добавлении новых строк.**

Цепочка событий при, например, нажатии кнопки "Add Row" (`AddRowCommand`):

1. `AddRow()` → `Rows.Add(row)` (`MainViewModel.cs:420`) — структурное изменение `ObservableCollection<PartRow>`.
2. Срабатывает `OnRowsCollectionChanged` (`MainViewModel.cs:269`) → так как `_suspendRecompute == false` (единичное добавление, не batch), вызывается `RecomputeSectionNumbers()` **и** `RecomputeDuplicateNumbers()`.
3. `RecomputeSectionNumbers()` (`MainViewModel.cs:343-355`) в конце вызывает `RowsView.Refresh()` — принудительный полный `Reset` сгруппированного/отсортированного `ListCollectionView`.
4. WPF в ответ на `Reset` **уничтожает все существующие контейнеры групп (`GroupItem`) и строк** и создаёт их заново — для *всех* строк и групп, а не только для новой строки, потому что: (а) `Refresh()` не различает "добавилась одна строка" от "поменялось всё"; (б) `EnableRowVirtualization="False"`/`EnableColumnVirtualization="False"` (C3) гарантируют, что абсолютно все строки во всех группах реализуются заново одновременно, а не по мере скролла.
5. Каждый новый `GroupItem` рендерится через `ControlTemplate` из `SectionGroupItemStyle`, где создаётся **новый `Expander`**. Так как этот `Expander` не изолирован от глобальных implicit-стилей MaterialDesign (C1), он получает полный MaterialDesign-вид ToggleButton-заголовка вместе с встроенной анимацией/переходом раскрытия содержимого. Поскольку контейнер создаётся заново "с нуля" на каждый `Refresh()`, control проходит через свой стартовый layout-цикл (сворачивание/разворачивание по умолчанию до применения `IsExpanded="True"`), прежде чем визуально "устаканиться" в развёрнутом виде.
6. Визуально это проявляется как то, что описывает пользователь: на короткое время (или до следующего действия, если строки добавляются быстро подряд, например через Paste построчно без батчинга) все строки/разделы таблицы "схлопываются"/уменьшаются по высоте, после чего раскладка окна временно выглядит некорректной — потому что вся таблица (`Height="*"` в `Grid.Row=8`, см. `MainWindow.xaml:213`) для одного/нескольких кадров рендерит контент в переходном (не полностью развёрнутом) состоянии, а строки-заголовки/разделители Grid выше и ниже (`Auto`) не меняют размер, создавая ощущение, что именно таблица "просела".

**Итог**: это не единичная опечатка в `Height`/`RowDefinitions` — цепочка из трёх факторов (C1 + C2 + C3) вместе даёт наблюдаемый эффект. Устранение только одного из них, скорее всего, не уберёт проблему полностью:
- C1 без C2/C3 — Expander по-прежнему будет пересоздаваться на каждый Refresh, просто без лишней анимации (сожмёт видимый эффект, но не устранит лишнюю перестройку/лаги).
- C2 без C1 — реже будет дёргаться анимация, но при добавлении строки, меняющей число групп (новый материал), Refresh всё равно потребуется.
- C3 без C1/C2 — с виртуализацией строк заново будут пересоздаваться только видимые строки, что уменьшит область "схлопывания", но исходная причина (implicit Expander style + Refresh) останется.

Правильный порядок исправления — см. Refactoring Plan.

## Important Improvements

### Архитектура
- **MVVM соблюдён на уровне разделения View/ViewModel**, но `MainViewModel` (~740 строк) уже сейчас взял на себя слишком много обязанностей: работа с файлами (`OpenFileDialog`/`SaveFileDialog`/`FolderBrowserDialog`), Excel-импорт, буфер обмена, undo-стек, раскрой, экспорт, локализация настроек — классический "God ViewModel". Стоит выделить хотя бы Import/Export-сценарии (`PasteFromClipboard`, `ImportExcelFile`, `SaveProject`, `OpenProject`) в отдельный сервис/фасад, а `MainViewModel` оставить оркестрацией и состоянием UI.
- Приватные вспомогательные классы `MaterialIdToNameConverter` и `RowSectionComparer` объявлены прямо в файле `MainViewModel.cs` (строки 710–741) — по конвенции проекта (`Converters/*.cs` для конвертеров) их стоит вынести в собственные файлы в `Converters/`, чтобы не искать их "внутри" ViewModel.

### MVVM
- `MaterialsViewModel.SelectedLibraryMaterial`/`SelectedProjectMaterial` — обычные auto-properties без вызова `OnPropertyChanged` в сеттере (`MaterialsViewModel.cs:26-27`), при этом `MoveToProjectCommand`/`DeleteFromLibraryCommand` и т.п. зависят от их значения в `CanExecute`. Работает только благодаря тому, что `RelayCommand.CanExecuteChanged` подписан на `CommandManager.RequerySuggested`, который переопрашивает состояние команд на **любое** UI-событие (клик, фокус) — то есть команды пересчитываются "случайно попадая" в нужный момент, а не детерминированно по изменению выбранного элемента. Пока это работает, но это хрупкий паттерн: если выбор материала будет меняться программно (не через клик пользователя), кнопки не обновятся вовремя.
- `RowSectionComparer.Compare` (`MainViewModel.cs:735-740`) на каждое сравнение вызывает `_owner.GetMaterialOrder(...)`, который делает **линейный проход по `Materials`** (`MainViewModel.cs:236-241`). При сортировке `n` строк это `O(n log n × m)` операций (`m` — число материалов), выполняемых на каждый `Refresh()` (см. C2) — при регулярном использовании с большими списками деталей это заметная лишняя нагрузка. Стоит закешировать `Dictionary<string,int>` порядка материалов и обновлять его только при изменении `Materials`.

### Производительность
- См. C2/C3 — совокупность "полный Refresh на каждое действие" + "виртуализация выключена" не масштабируется: при росте числа деталей (сотни строк, что для раскроя мебельного производства реалистично) каждое добавление/перенос строки будет линейно дороже.
- `PasteFromClipboard`/`ImportExcelFile` корректно используют `AddRowsBatch` с `_suspendRecompute` (одна перестройка на всю операцию, комментарий на `MainViewModel.cs:293-297` прямо объясняет, почему это важно) — то есть команда уже понимает проблему и решила её для batch-сценария, но не для одиночного `AddRow`/`MoveRowToMaterial`/смены материала в ячейке, где `Refresh()` всё равно летит на каждое единичное изменение.

### Читаемость XAML
- `MainWindow.xaml` — один файл на ~340 строк с инлайновыми стилями, DataTemplate'ами и бизнес-комментариями о ширинах колонок в XML-комментарии в самом верху файла (строки 14–19) — сложно поддерживать: ширины уже задокументированы в 3 разных местах (комментарий, атрибуты `Width` на колонках, и потенциально в `docs/UI_Design_System.md`). Стоит вынести повторяющиеся `Style` (`SectionGroupItemStyle`, `PartRowStyle`, `MaterialChipStyle`) в отдельный `ResourceDictionary` (например, `MainWindowStyles.xaml`), подключаемый через `MergedDictionaries`, чтобы `MainWindow.xaml` содержал только структуру, а не стили.
- Внутренние `Grid` с `RowDefinitions`/`ColumnDefinitions` из "Auto/6/Auto/6/Auto" (например, строки 131-135, 166-170) повторяются в нескольких местах почти один в один (двухстрочная форма "лейбл — поле — кнопка") — кандидат на `UserControl`/`DataTemplate` "LabeledPathPicker", что уберёт 3-4 копии одинаковой Grid-разметки.

## Refactoring Plan

Порядок важен: сначала устраняется корневая причина (C1), затем убирается избыточность, которая её усиливала (C2, C3), и только потом — общие улучшения архитектуры. Без кода, только последовательность действий:

1. **Изолировать `Expander` в `SectionGroupItemStyle` от глобальных implicit-стилей MaterialDesign** (C1) — минимальное, наиболее целевое исправление; проверить, исчезает ли визуальное "схлопывание" уже после этого шага.
2. **Проверить необходимость `RowsView.Refresh()` в `RecomputeSectionNumbers()` при единичных изменениях** (C2) — определить, в каких случаях группировка/сортировка обновляется автоматически через `ObservableCollection`-уведомления, и убрать `Refresh()` там, где это не обязательно; оставить принудительный `Refresh()` только там, где меняется сам состав/порядок групп (например, после `Materials.CollectionChanged`).
3. **Замерить эффект и рассмотреть возврат `EnableRowVirtualization="True"`** (C3) — только после шагов 1–2, чтобы не тестировать виртуализацию поверх исходного бага.
4. **Кэшировать порядок материалов** для `RowSectionComparer`/`GetMaterialOrder`, чтобы убрать линейный поиск на каждое сравнение при сортировке.
5. **Устранить дублирование drag&drop-кода** между `MainWindow.xaml.cs` и `MaterialsWindow.xaml.cs` (C4) — выделить общий хелпер.
6. **Вынести `MaterialIdToNameConverter` и `RowSectionComparer`** из `MainViewModel.cs` в `Converters/`/отдельные файлы согласно существующей структуре проекта.
7. **Провести ревизию `MaterialsViewModel`** — добавить явные вызовы `OnPropertyChanged` для `SelectedLibraryMaterial`/`SelectedProjectMaterial`, чтобы не полагаться только на `CommandManager.RequerySuggested`.
8. **Вынести повторяющиеся стили `MainWindow.xaml`** (`SectionGroupItemStyle`, `PartRowStyle`, `MaterialChipStyle`) в отдельный `ResourceDictionary`, чтобы разгрузить основной XAML-файл.
9. (Опционально, более крупный рефакторинг) **Разгрузить `MainViewModel`**, выделив Import/Export/Undo-логику в отдельные сервисы — снижает риск регрессий при дальнейших изменениях UI и упрощает тестирование.

После создания этого отчёта — остановка, изменения в коде не вносятся до отдельного подтверждения.
