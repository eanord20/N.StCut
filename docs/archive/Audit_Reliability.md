# Reliability Audit — N.StCut

Аудит проведён как Senior C# / WPF Reliability Engineer. Цель — оценить устойчивость приложения к сбоям (необработанные исключения, повреждение данных, файловый I/O, поведение при некорректном вводе) с учётом приоритета проекта "Stable production behavior" (`AGENTS.md`). **Код не изменялся — только анализ.** Документ дополняет `docs/Audit_Architecture.md` и `docs/Audit_Performance.md`, не повторяя их выводы.

---

# Общая оценка надёжности: 4/10

В приложении отсутствует **единая стратегия обработки ошибок**: обработка исключений сделана только вокруг одной операции (`Nest()`), тогда как большинство файловых операций (экспорт DXF, экспорт отчёта, сохранение/открытие проекта, импорт Excel, поиск файлов) не защищены от исключений вообще. Поскольку в приложении **нет глобального обработчика необработанных исключений** (`Application.DispatcherUnhandledException` не подписан), любое необработанное исключение в обработчике команды приведёт к аварийному завершению всего процесса — без возможности сохранить несохранённые данные пользователя. Отдельно есть риски целостности данных при записи файлов (не атомарная запись настроек/библиотеки/проекта) и рассинхронизация в обработке одного и того же класса ошибок (`AppSettingsService` защищён от повреждённого файла, `ProjectFileService` — нет).

## Critical Issues

### R1. Отсутствует глобальный обработчик необработанных исключений — любой сбой завершает процесс без сохранения данных

- **Файл**: <ref_file file="D:\My_project\N.StCut\src\NStCut.App\App.xaml.cs" />
- **Описание**: `App` не переопределяет/не подписывается на `DispatcherUnhandledException`, `AppDomain.CurrentDomain.UnhandledException` или `TaskScheduler.UnobservedTaskException`. Единственная защита от исключений в приложении — локальный `try/catch` внутри `Nest()` (см. R2). Любое необработанное исключение в любом другом обработчике команды (см. R2 — таких большинство) приводит к падению процесса.
- **Влияние**: пользователь, работающий над списком из сотен деталей, потеряет все несохранённые изменения (нет автосохранения) при любом непредвиденном сбое — например, повреждённый DXF-файл, недоступная сетевая папка, переполненный диск при экспорте. Это прямо противоречит приоритету проекта "Stable production behavior" (`AGENTS.md`).
- **Рекомендация**: добавить обработчик `Application.DispatcherUnhandledException` (как минимум — логировать и показать пользователю диалог с возможностью попытаться сохранить проект перед закрытием), не как замену точечной обработке (R2), а как последний рубеж защиты.

### R2. Большинство файловых операций не обёрнуты в обработку исключений — только `Nest()` защищён

- **Файл**: <ref_file file="D:\My_project\N.StCut\src\NStCut.App\ViewModels\MainViewModel.cs" />
- **Незащищённые методы** (нет `try/catch` вокруг файлового/внешнего I/O):
  - `ExportDxf()` (строки 620–631) — вызывает `_dxfExport.WriteSheet` для каждого листа; исключение (например, занятый файл, отсутствие прав на папку, поврежденный исходный DXF внутри `DxfExportService.WriteSheet`) прервёт цикл без перехвата.
  - `ExportReport()` (строки 633–648) — вызывает `_reportService.GenerateReport` (использует стороннюю библиотеку DocX) без защиты.
  - `SaveProject()`/`OpenProject()` (строки 662–697) — `JsonSerializer.Deserialize` в `ProjectFileService.Load` может бросить `JsonException` на повреждённом/невалидном `.nstcut`-файле, ничем не перехватывается по пути до UI.
  - `ImportExcelFile()` (строки 517–550) — `ExcelReaderFactory.CreateReader`/`reader.Read()` на повреждённом `.xlsx` или файле, занятом другим процессом (открыт в Excel), бросит исключение без перехвата.
  - `FindFiles()` (строки 476–491) — `Directory.EnumerateFiles` внутри `FileResolveService.GetCandidates` при рекурсивном обходе (`SearchOption.AllDirectories`) может бросить `UnauthorizedAccessException` на недоступной вложенной папке (типичная ситуация для расшаренных сетевых дисков) — исключение всплывёт до `FindFiles()`, не перехватывается.
  - `SelectFileManually`/`SelectAmbiguousFile`/`BrowseSearchPath`/`BrowseOutputPath` — диалоги ОС сами по себе безопасны, но последующие файловые операции (например, будущее использование выбранного пути) не проверяются на исключения.
- **Единственное исключение** — `Nest()` (строки 573–618) обёрнут в `try/catch (Exception ex)` с `MessageBox.Show(ex.Message, "Nesting error", ...)`, но и здесь есть недостаток: перехват идёт **вокруг всей операции целиком**, включая чтение геометрии всех деталей — если один-единственный DXF-файл повреждён, весь раскрой прерывается с общим сообщением об ошибке, вместо того чтобы пропустить проблемную деталь (пометить `NotFound`/ошибкой) и продолжить с остальными.
- **Влияние**: несогласованная защита — одна операция (`Nest`) частично защищена, остальные пять — нет; пользователь получает либо аварийное завершение процесса (R1), либо (в лучшем случае, для `Nest`) прерывание всей операции из-за одного проблемного файла.
- **Рекомендация**: ввести единый паттерн обработки ошибок команд (например, обёртка в самом `RelayCommand`/базовом методе выполнения команды, логирующая и показывающая пользователю понятное сообщение без падения процесса), и для `Nest()` — обрабатывать ошибку чтения контура на уровне отдельной детали, а не всей операции.

### R3. Несогласованная защита от повреждённых конфигурационных файлов между похожими сервисами

- **Файлы**: <ref_file file="D:\My_project\N.StCut\src\NStCut.App\Services\AppSettingsService.cs" /> (строки 22–37) vs <ref_file file="D:\My_project\N.StCut\src\NStCut.App\Services\ProjectFileService.cs" /> (строки 23–28) и <ref_file file="D:\My_project\N.StCut\src\NStCut.App\Services\MaterialsLibraryService.cs" /> (строки 22–29)
- **Описание**: `AppSettingsService.Load()` явно оборачивает чтение/десериализацию в `try/catch` и возвращает `new AppSettings()` при любой ошибке, с комментарием *"Повреждённый/несовместимый файл настроек не должен мешать запуску приложения"* — осознанное защитное решение. `ProjectFileService.Load()` и `MaterialsLibraryService.Load()` делают то же самое (`File.ReadAllText` + `JsonSerializer.Deserialize`), но **без** такой защиты — повреждённый `.nstcut`-проект или `materials-library.json` (например, вручную отредактированный пользователем, либо повреждённый из-за сбоя при записи, см. R4) приведёт к необработанному исключению.
- **Влияние**: непоследовательное поведение — один и тот же класс проблемы ("файл настроек испорчен") обрабатывается по-разному в зависимости от того, какой именно файл повреждён; для `MaterialsLibraryService` это особенно critical, так как она **загружается автоматически** при каждом открытии окна "Материалы" (`MaterialsViewModel` конструктор) — то есть повреждённый файл библиотеки материалов заблокирует эту функциональность (или уронит процесс, см. R1) при каждой попытке её открыть.
- **Рекомендация**: применить одинаковый защитный паттерн (try/catch с понятным сообщением пользователю и восстановлением через пустое состояние по умолчанию, как уже сделано в `AppSettingsService`) во всех трёх сервисах.

### R4. Неатомарная запись файлов настроек/библиотеки/проекта — риск повреждения при сбое посреди записи

- **Файлы**: <ref_file file="D:\My_project\N.StCut\src\NStCut.App\Services\AppSettingsService.cs" /> (строка 42, `File.WriteAllText`), <ref_file file="D:\My_project\N.StCut\src\NStCut.App\Services\MaterialsLibraryService.cs" /> (строка 34), <ref_file file="D:\My_project\N.StCut\src\NStCut.App\Services\ProjectFileService.cs" /> (строка 20)
- **Описание**: все три сервиса пишут напрямую через `File.WriteAllText(path, json)`. Это не атомарная операция — если процесс завершится аварийно (см. R1) или произойдёт сбой питания/диска ровно во время записи, файл может остаться частично записанным (обрезанный JSON), что при следующем запуске приведёт к ошибке десериализации (усугубляется R3 для `ProjectFileService`/`MaterialsLibraryService`, где эта ошибка ничем не перехватывается).
- **Влияние**: пользователь может потерять сохранённый проект или библиотеку материалов из-за случайного стечения обстоятельств (сбой ровно в момент сохранения), без какого-либо резервного варианта восстановления.
- **Рекомендация**: писать во временный файл и атомарно переименовывать (`File.Move` с заменой) поверх целевого файла — стандартный паттерн "безопасной записи", устраняющий промежуточное повреждённое состояние.

### R5. Экспорт DXF не атомарен на уровне всей операции — частичный набор файлов на диске при сбое в середине цикла

- **Файл**: <ref_snippet file="D:\My_project\N.StCut\src\NStCut.App\ViewModels\MainViewModel.cs" lines="620-631" /> (`ExportDxf`)
- **Описание**: `ExportDxf()` пишет DXF-файлы по одному на лист в цикле `foreach (var sheet in _nestingResult.Sheets)`. Если запись прерывается исключением на середине (см. R2 — не перехватывается), на диске остаётся набор из части листов, экспортированных, и части — нет, без явного индикатора для пользователя, какие именно листы уже записаны, а какие нет.
- **Влияние**: пользователь может не заметить, что экспорт завершился частично (особенно в сочетании с R1 — если процесс упадёт, то не будет даже сообщения об ошибке), и уйти в резку с неполным комплектом файлов.
- **Рекомендация**: как минимум — сообщать пользователю, на каком шаге (индексе листа) произошла ошибка, если она произошла; в перспективе — записывать во временную подпапку и переносить только при полном успехе всех листов.

|---|---|---|---|
| `Nest()` | Да (строки 576–617) | `MessageBox` с `ex.Message`, `IsBusy=false` в `finally` | Перехват на уровне всей операции, не отдельной детали (см. R2) |
| `ExportDxf()` | Нет | Необработанное исключение → падение процесса (R1) | См. R2, R5 |
| `ExportReport()` | Нет | Необработанное исключение → падение процесса | См. R2 |

| `OpenProject()` | Нет | Необработанное исключение при повреждённом файле → падение процесса | `ProjectFileService.Load` не защищён (R3) |
| `ImportExcelFile()` | Нет | Необработанное исключение (повреждённый/занятый файл) → падение процесса | См. R2 |

| `AppSettingsService.Load()` | Да | Возврат `new AppSettings()` | Единственный образец правильного паттерна в проекте |

| `ProjectFileService.Load()` | Нет | Необработанное исключение | См. R3 |
| Приложение в целом (`App.xaml.cs`) | Нет глобального обработчика | Падение процесса на любое необработанное исключение | См. R1 |

## Data Integrity

- Запись `.nstcut`, `materials-library.json`, `app-settings.json` — неатомарна (R4).
- Формат проекта уже поддерживает миграцию старой схемы (`ProjectFileService.MigrateLegacyPartNames`) — это хороший задел для эволюции формата данных, но сама миграция также не защищена от исключений при парсинге невалидного JSON (`JsonNode.Parse(json)` может бросить исключение на действительно повреждённом файле, не перехватывается).
- `PushUndoSnapshot`/`Undo` (описаны подробнее в `docs/Audit_Performance.md`, issue P3) — с точки зрения надёжности это плюс: полное копирование состояния перед каждым изменением защищает от частичного/несогласованного состояния при отмене, ценой производительности.
- Раскрой (`BoundingBoxShelfEngine`) — детерминирован (сортировка по площади, стабильный порядок групп), что соответствует требованию проекта "Results must be deterministic" — с точки зрения надёжности воспроизводимости результатов раскроя нареканий нет.

## Crash Resilience

- Нет глобального обработчика необработанных исключений (R1) — главный риск для стабильности в продакшене.
- Нет автосохранения/восстановления после сбоя — при падении процесса весь несохранённый список деталей/материалов теряется безвозвратно.
- `Nest()` — единственное место с частичной защитой, но при этом `IsBusy` сбрасывается в `finally`, что корректно предотвращает "зависшее" состояние UI после ошибки (это сделано правильно).
- Сетевые операции (`UpdateService.IsUpdateAvailableAsync`) корректно оборачивают HTTP-запрос в `try/catch` и проглатывают ошибку (сервис фактически не используется — см. `docs/Audit_Architecture.md`, issue A4 — но сам защитный паттерн внутри написан правильно).

## Рекомендации

### Critical
1. Добавить глобальный обработчик `Application.DispatcherUnhandledException` (R1) — минимальный рубеж защиты от падения процесса с потерей данных пользователя.
2. Обернуть незащищённые файловые операции (`ExportDxf`, `ExportReport`, `SaveProject`, `OpenProject`, `ImportExcelFile`, `FindFiles`) в единообразную обработку ошибок команд (R2).
3. Выровнять защиту от повреждённых файлов между `AppSettingsService`, `ProjectFileService`, `MaterialsLibraryService` — все три должны одинаково не падать на невалидном JSON (R3).

### Important
1. Атомарная запись файлов настроек/библиотеки/проекта через временный файл + `File.Move` (R4).
2. Обрабатывать ошибку чтения геометрии одной детали в `Nest()` как ошибку конкретной детали (пометить статус), а не прерывать весь раскрой целиком (R2, детализация).
3. Сообщать пользователю, на каком шаге прервался `ExportDxf()`, если экспорт завершился частично (R5).

### Future
1. Автосохранение/восстановление состояния проекта на случай сбоя (снижает последствия R1 даже после внедрения глобального обработчика).
2. Логирование необработанных исключений (файл лога) для последующей диагностики сбоев в продакшене, раз глобальный обработчик всё равно будет их перехватывать (R1).
