# Performance Audit — N.StCut

Аудит проведён как Senior Desktop Performance Engineer. Цель — найти узкие места, которые будут ограничивать скорость работы при росте числа DXF-деталей (сотни–тысячи строк/файлов). **Код не изменялся — только анализ.** Документ дополняет (не дублирует детали) `docs/Code_Audit_UI.md` (там подробно разобран баг `GroupStyle`/`Refresh()`/`Expander`) и `docs/Audit_Architecture.md`.

---

# Общая оценка производительности: 5/10

Для небольших проектов (десятки деталей) приложение будет работать гладко. Но заложено сразу несколько операций с линейной или худшей стоимостью, выполняемых **синхронно на UI-потоке** и **без кеширования**, которые при росте количества деталей до сотен/тысяч (что реалистично для мебельного производства) будут давать заметные, а местами блокирующие UI задержки:

1. Поиск DXF-файлов пересканирует диск **на каждую строку** вместо одного прохода.
2. Чтение геометрии (`Nest`) и запись DXF (`ExportDxf`) выполняются синхронно на UI-потоке без `Task.Run`/`async`, блокируя интерфейс на время, пропорциональное числу деталей.
3. Undo-стек хранит до 50 полных глубоких копий всего списка деталей, создаваемых синхронно **на каждое** структурное изменение (включая перетаскивание одной строки).
4. `DataGrid` работает без виртуализации строк/колонок в сочетании с частыми `CollectionView.Refresh()` (см. `docs/Code_Audit_UI.md`, issue C2/C3) — стоимость перерисовки растёт с числом строк быстрее, чем должна.
5. Алгоритм раскроя (`ShelfPacker`) — приемлемая, но не лучшая асимптотика для размещения (см. Complexity Analysis).

## Bottlenecks

### P1. Поиск файлов пересканирует всю папку на каждую строку — O(rows × files-on-disk)

- **Файл**: <ref_file file="D:\My_project\N.StCut\src\NStCut.App\Services\FileResolveService.cs" />, метод `GetCandidates` (строки 19–50)
- **Вызывается из**: <ref_snippet file="D:\My_project\N.StCut\src\NStCut.App\ViewModels\MainViewModel.cs" lines="476-491" /> (`FindFiles()`) — `foreach (var row in Rows...) _fileResolveService.Resolve(...)`
- **Причина**: `GetCandidates` при каждом вызове делает `Directory.EnumerateFiles(searchPath, "*.dxf", SearchOption.AllDirectories)` — полный рекурсивный обход файловой системы. `FindFiles()` вызывает `Resolve` (который вызывает `GetCandidates`) **отдельно для каждой строки таблицы**, то есть при 500 деталях папка с DXF-файлами сканируется 500 раз подряд.
- **Влияние**: если в папке поиска тысячи файлов (реалистично для архива деталей производства), время `FindFiles()` растёт как `O(rows × files)` вместо `O(files + rows)`. На сетевых папках (частый сценарий для производства — общий сетевой диск с DXF) это может превратить операцию из секунд в минуты.
- **Приоритет**: **High**.

### P2. `Nest()` и `ExportDxf()` выполняются синхронно на UI-потоке — блокировка интерфейса пропорциональна числу деталей

- **Файл**: <ref_snippet file="D:\My_project\N.StCut\src\NStCut.App\ViewModels\MainViewModel.cs" lines="573-618" /> (`Nest()`), <ref_snippet file="D:\My_project\N.StCut\src\NStCut.App\ViewModels\MainViewModel.cs" lines="620-631" /> (`ExportDxf()`)
- **Причина**: `RelayCommand` вызывает делегат синхронно на потоке, из которого была нажата кнопка (UI-поток). `Nest()` в цикле `foreach (var part in parts)` для каждой детали читает DXF-файл целиком (`_dxfGeometry.ReadContour` → `DxfDocument.Load` в <ref_file file="D:\My_project\N.StCut\src\NStCut.Dxf\Services\DxfGeometryService.cs" /> строка 15) — операция диск+CPU-парсинг, без `await`/`Task.Run`. `IsBusy = true` (строка 575) выставляется, но так как поток занят синхронным циклом, диспетчер WPF не может перерисовать UI (в том числе индикатор занятости/прогресс-бар) до завершения всего цикла — `IProgress<double>` (строка 600) физически не сможет отрисовать промежуточные значения, пока UI-поток заблокирован.
- **Аналогично** `ExportDxf()` (<ref_file file="D:\My_project\N.StCut\src\NStCut.Dxf\Services\DxfExportService.cs" />, `WriteSheet`) — для каждой размещённой детали **заново** загружает исходный DXF-файл целиком (`DxfDocument.Load(placed.Source.DxfPath)`, строка 43) внутри `WritePlacedPart`, вызываемого в цикле по всем деталям листа — без какого-либо прогресс-репортинга вообще (в отличие от `Nest`, тут нет даже `IProgress`).
- **Влияние**: при сотнях деталей UI "замирает" (не отвечает на ввод, не перерисовывается) на время чтения/записи всех DXF — воспринимается пользователем как зависание программы.
- **Приоритет**: **High**.

### P3. Undo-снэпшот — полное глубокое копирование всего списка деталей на каждое единичное действие

- **Файл**: <ref_snippet file="D:\My_project\N.StCut\src\NStCut.App\ViewModels\MainViewModel.cs" lines="370-376" /> (`PushUndoSnapshot`)
- **Вызывается из**: `AddRow`, `DeleteSelectedRows`, `SelectFileManually`, `SelectAmbiguousFile`, `PasteFromClipboard`, `OpenProject`, и что особенно важно — `MoveRowToMaterial` (строка 263), то есть **на каждый Drag&Drop одной строки между разделами**.
- **Причина**: `_undoStack.AddLast(Rows.Select(r => r.Clone()).ToList())` — создаёт новый `List<PartRow>` из клонов **всех** строк таблицы, независимо от того, что реально изменилось (даже для переноса одной строки клонируются все остальные). `MaxUndoDepth = 50` — то есть в худшем случае в памяти одновременно держится 50 полных копий списка деталей.
- **Влияние**: при 1000 строк каждое перетаскивание/добавление/удаление синхронно выполняет 1000 аллокаций объектов `PartRow` (плюс GC-нагрузка) прямо в обработчике UI-события — на медленных машинах это заметная микро-задержка на каждое взаимодействие с таблицей, а на 50 накопленных снэпшотах — до 50 000 живых объектов `PartRow`, удерживаемых в памяти только ради undo.
- **Приоритет**: **Medium** (заметно при больших списках, но не блокирует, в отличие от P1/P2).

### P4. `DataGrid` без виртуализации + принудительный `CollectionView.Refresh()` на каждое изменение

- **Файл**: <ref_file file="D:\My_project\N.StCut\src\NStCut.App\MainWindow.xaml" />, строка 243 (`EnableRowVirtualization="False" EnableColumnVirtualization="False"`)
- **Причина**: подробно разобрано в `docs/Code_Audit_UI.md` (issues C1–C3) как источник визуального бага; с точки зрения производительности это означает, что **все** строки во **всех** группах всегда полностью реализованы как визуальные элементы (`DataGridRow` + все ячейки/контролы внутри, включая `ComboBox` материала/текстуры, `Expander` заголовков групп) — независимо от прокрутки. Каждый `RowsView.Refresh()` (вызывается почти на каждое изменение, см. `Code_Audit_UI.md` issue C2) пересоздаёт все эти визуальные элементы заново.
- **Влияние**: стоимость каждого обновления таблицы растёт линейно с полным количеством строк, а не с количеством видимых строк — на больших списках (сотни+ строк) это ощутимо медленнее, чем при включённой виртуализации.
- **Приоритет**: **High** (для этой конкретной аудитории — "много DXF деталей" — это один из главных лимитирующих факторов).

### P5. `RowSectionComparer`/`GetMaterialOrder` — линейный поиск на каждое сравнение при каждой сортировке

- **Файл**: <ref_snippet file="D:\My_project\N.StCut\src\NStCut.App\ViewModels\MainViewModel.cs" lines="234-241" /> (`GetMaterialOrder`), <ref_snippet file="D:\My_project\N.StCut\src\NStCut.App\ViewModels\MainViewModel.cs" lines="729-741" /> (`RowSectionComparer.Compare`)
- **Причина**: `GetMaterialOrder` делает `for (int i = 0; i < Materials.Count; i++)` — линейный проход по списку материалов. Вызывается **дважды на каждое сравнение** во время сортировки `RowsView` (`CustomSort`), которая сама по себе `O(n log n)` по строкам — итоговая стоимость одной пересортировки `O(n log n × m)`, где `m` — число материалов.
- **Влияние**: при большом количестве материалов (десятки видов ДСП/ЛДСП на реальном производстве) и большом числе строк — заметная лишняя нагрузка на каждую пересортировку (а пересортировки происходят часто, см. P4/C2).
- **Приоритет**: **Medium**.

### P6. `CommandManager.RequerySuggested` — O(n) `CanExecute`-предикаты пересчитываются на каждое UI-событие

- **Файл**: <ref_file file="D:\My_project\N.StCut\src\NStCut.App\Commands\RelayCommand.cs" />, строки 16–20; предикат `CanNest()` — <ref_snippet file="D:\My_project\N.StCut\src\NStCut.App\ViewModels\MainViewModel.cs" lines="567-571" />
- **Причина**: `RelayCommand.CanExecuteChanged` подписан на статический `CommandManager.RequerySuggested`, который WPF поднимает на **каждое** значимое UI-событие (клик, движение фокуса, нажатие клавиши и т.д.) для **всех** зарегистрированных команд разом. `CanNest()` при этом делает `Rows.Any(r => !string.IsNullOrWhiteSpace(r.MaterialId))` — линейный проход по всем строкам на каждый такой пересчёт.
- **Влияние**: с ростом числа строк каждый клик/нажатие клавиши в приложении (не только в самой таблице) требует лишнего `O(n)` прохода. Для сотен строк это единицы миллисекунд на событие — по отдельности незаметно, но в сумме с P4/P5 (тоже завязанными на частые UI-события) добавляет к общей "тяжести" взаимодействия с большим списком.
- **Приоритет**: **Low**.

### P7. `SheetThumbnailService.Render` создаёт полноценное дерево WPF-визуалов (Canvas + N Rectangle) только для рендера в PNG для отчёта

- **Файл**: <ref_file file="D:\My_project\N.StCut\src\NStCut.App\Services\SheetThumbnailService.cs" />
- **Причина**: для каждого листа раскроя создаётся `Canvas` с полным набором `Rectangle`-элементов (по одному на деталь), выполняется `Measure`/`Arrange`/`RenderTargetBitmap.Render` — то есть используется тяжеловесный WPF visual/layout pipeline там, где для генерации растрового превью было бы значительно дешевле использовать `DrawingVisual`/`DrawingContext` напрямую (без создания реальных `UIElement` с их системой layout/binding/dependency properties).
- **Влияние**: при экспорте отчёта с большим числом листов (`ExportReport()` вызывает `Render` для каждого листа синхронно, строка 640 в `MainViewModel.cs`) — заметно медленнее, чем необходимо, плюс лишнее давление на GC от короткоживущих `UIElement`.
- **Приоритет**: **Medium**.

## Complexity Analysis

| Операция | Сложность | Комментарий |
|---|---|---|
| `FileResolveService.GetCandidates` (на 1 деталь) | O(F), F = файлов в папке поиска | Полный `Directory.EnumerateFiles` на каждый вызов |
| `MainViewModel.FindFiles()` (на весь список) | **O(R × F)** | R строк × полное сканирование папки на каждую (P1) |
| `DxfGeometryService.ReadContour` (на 1 файл) | O(E), E = сущностей в DXF | Линейный проход по entities, приемлемо |
| `MainViewModel.Nest()` — фаза чтения контуров | O(R × E̅) | R деталей × среднее число сущностей на DXF, синхронно на UI-потоке (P2) |
| `BoundingBoxShelfEngine.Nest` — сортировка копий по площади | O(C log C), C = суммарное число копий (с учётом Quantity) | `List.Sort` — стандартный `O(n log n)`, разумно |
| `ShelfPacker.TryPlace` (размещение одной детали) | O(K) в среднем, где K — деталей уже на текущей полке/листе (из-за `foreach (var packer in packers)` в `BoundingBoxShelfEngine.Nest`, строка 47) | Худший случай **O(P)**, P — число уже созданных листов для материала, т.к. перебираются все текущие `packers` по очереди |
| `BoundingBoxShelfEngine.Nest` — размещение всех копий одного материала | O(C × P), в худшем случае деградирует к **O(C²)** при большом числе листов | Нет пространственного индекса/эвристики "текущий активный лист" — каждая деталь пробует все ранее созданные листы по порядку |
| `RowSectionComparer.Compare` | O(M), M = число материалов (линейный поиск в `GetMaterialOrder`) | Вызывается на каждое сравнение при сортировке |
| `RowsView.Refresh()` (пересортировка + перегруппировка) | O(R log R × M) | С учётом P5; вызывается на каждое единичное изменение строки (см. `Code_Audit_UI.md`, C2) |
| `DataGrid` перерисовка при `Refresh()` (виртуализация выключена) | O(R_total), а не O(R_visible) | P4 — должно быть O(видимых строк) |
| `PushUndoSnapshot` | O(R) на каждый вызов, до 50 накопленных снэпшотов ⇒ до O(50×R) памяти | P3 |
| `DxfExportService.WriteSheet` (один лист) | O(Parts_on_sheet × E̅) — каждый раз читает DXF заново с диска | Нет кеша уже прочитанных `DxfDocument` (P2) |
| `SheetThumbnailService.Render` (один лист) | O(Parts_on_sheet) визуальных элементов + полный WPF layout pass | P7 |

## Memory Analysis

- **Undo-стек (P3)**: до `MaxUndoDepth = 50` полных копий `List<PartRow>` одновременно в памяти — при больших проектах (тысячи строк) это может быть счётно значимый объём (тысячи объектов `PartRow` × 50), особенно если пользователь активно перетаскивает/добавляет строки в течение сессии (стек постоянно "текёт": старые снэпшоты вытесняются, GC вынужден периодически собирать десятки тысяч мёртвых объектов).
- **`DataGrid` без виртуализации (P4)**: все визуальные контейнеры строк/ячеек живут в памяти одновременно для всех строк всех групп — включая вложенные `ComboBox`/`TextBox`/`Button` на каждую строку (10 колонок × N строк визуальных элементов). Для 1000 строк это тысячи живых `FrameworkElement` вместо десятков (сколько реально видно на экране).
- **`DxfExportService.WriteSheet` (P2)**: каждый исходный DXF загружается в памяти как полный `DxfDocument` (netDxf), клонируется entity-по-entity и тут же отбрасывается — при большом количестве деталей на листе это всплески аллокаций netDxf-объектов, не переиспользуемые между вызовами (нет кеша "уже загруженный DxfDocument для пути X" на время экспорта одного `ExportDxf()` вызова, хотя один и тот же исходный файл может встретиться на разных листах при `Quantity > 1`).
- **IDisposable**: `FolderBrowserDialog` корректно оборачивается в `using` (<ref_snippet file="D:\My_project\N.StCut\src\NStCut.App\ViewModels\MainViewModel.cs" lines="396-414" />) — хорошая практика. `HttpClient` в `UpdateService` (<ref_file file="D:\My_project\N.StCut\src\NStCut.App\Services\UpdateService.cs" />, строка 12) создаётся как поле и никогда не освобождается — некритично, так как сервис живёт всё время работы приложения (один экземпляр), но сам сервис фактически не используется (см. `docs/Audit_Architecture.md`, issue A4), поэтому сейчас это не создаёт реальной нагрузки.
- **COM**: COM-объекты в UI-слое не используются (`System.Windows.Forms.FolderBrowserDialog` — управляемая обёртка, не прямой COM-вызов) — рисков, специфичных для COM (актуальных для Inventor/SolidWorks-интеграций, упомянутых в глобальных правилах проекта), в текущем коде не найдено, так как такой интеграции пока нет.
- **Явных утечек памяти (незакрытых подписок на события, приводящих к удержанию объектов дольше жизненного цикла) не найдено** — `MainViewModel.OnRowsCollectionChanged` аккуратно отписывает/подписывает `PropertyChanged` на удаляемых/добавляемых строках (строки 271–284), а WPF-биндинги на `INotifyPropertyChanged` используют weak-event по умолчанию.

## UI Rendering

- **Virtualization**: отключена (`EnableRowVirtualization="False"`, `EnableColumnVirtualization="False"`) — главный рычаг по производительности рендеринга при росте числа строк (P4). Колонок немного (10, фиксированной ширины) — отключение column-virtualization менее критично, но row-virtualization стоит вернуть после устранения бага с `GroupStyle` (см. `docs/Code_Audit_UI.md`).
- **Canvas** (`SheetPreviewWindow.xaml`, `ItemsControl` с `Canvas` в качестве `ItemsPanel`) — для предпросмотра раскроя рисуется один `Rectangle` на деталь без виртуализации (обычный `ItemsControl`, не `VirtualizingStackPanel`) — приемлемо, так как количество деталей на одном листе обычно на порядок меньше, чем общее число строк в проекте, но при очень плотных раскроях (сотни деталей на лист) стоит иметь в виду тот же принцип, что и для `DataGrid`.
- **ScrollViewer**: явных случаев "ScrollViewer внутри ScrollViewer" (классический источник проблем с `CanContentScroll`/бесконечной высотой при измерении) не найдено — `DataGrid` использует встроенный `ScrollViewer`, `SheetPreviewWindow` оборачивает `Canvas` в `ScrollViewer` без дополнительной вложенности.
- **Перерасчёт Layout / лишние перерисовки**: помимо `Refresh()` (P4), не найдено сценариев с бесконечными циклами `Measure`/`Arrange` или анимаций, работающих постоянно (`Storyboard` не используются в проекте напрямую — единственная потенциальная анимация приходит implicit-стилем `Expander`, см. `docs/Code_Audit_UI.md`, C1).
- **DataGrid `RowStyle` с `Background` через `Binding + Converter`** (`StatusToBrushConverter`) — конвертер вызывается на каждый re-render строки; сам по себе дешёвый (`switch`), не является узким местом.

## Приоритет оптимизаций

### High Impact
1. **P1** — кешировать один `Directory.EnumerateFiles` результат на весь вызов `FindFiles()` вместо пересканирования папки на каждую строку.
2. **P2** — перенести чтение DXF-контуров (`Nest`) и запись листов (`ExportDxf`) на фоновый поток (`Task.Run`/`async`), чтобы UI не блокировался и прогресс реально отображался.
3. **P4** — вернуть `EnableRowVirtualization="True"` после устранения причины отключения (баг `GroupStyle`, см. `docs/Code_Audit_UI.md`), чтобы стоимость обновления таблицы не росла линейно с полным числом строк.

### Medium
1. **P3** — снизить стоимость Undo: либо не клонировать весь список на каждое мелкое действие (например, хранить только дельту изменения — старое значение поля/позицию строки), либо ограничить создание снэпшота только для действительно "тяжёлых" операций.
2. **P5** — кешировать порядок материалов (`Dictionary<string,int>`) вместо линейного поиска в `GetMaterialOrder` при каждом сравнении.
3. **P7** — заменить `Canvas`+`UIElement`-рендеринг в `SheetThumbnailService` на прямую отрисовку через `DrawingVisual`/`DrawingContext`, минуя полноценный WPF layout pipeline.
4. **Кеш `DxfDocument`** в `DxfExportService.WriteSheet` — не перечитывать один и тот же исходный DXF-файл повторно, если он встречается на нескольких местах листа/в нескольких листах (актуально при `Quantity > 1`).

### Low
